## Findings

1. **M0P1a-01 — High — stale authentication purges a newer authorized binding.** `Madar/App/MadarLock.swift:123–128`. Reproducible ordering with the existing controlled verifier: A waits in `verify`; background invalidates A; active re-entry and B successfully authorize/rebind; A then returns success, fails `current()`, and the stale catch unconditionally enqueues a global purge. B stays unlocked and uncovered while its service binding is removed. A never bound rows in this sequence, so its late result has no data that needs purging. The same unowned purge is unsafe after a genuinely stale asynchronous binding unless exposure is held closed until cleanup and current rebinding finish. **Fix:** distinguish requests that reached service binding from those rejected before binding; do not let a stale verifier alter a newer request's data/state. Serialize required stale-binding cleanup with current recovery/authorization, cover synchronously while cleanup is pending, and permit exposure only after the current binding is restored. Add `test_M0P1a_staleVerifierCannotPurgeNewAuthorization` and a delayed-service stale-binding variant. Assert the newer binding, ticket and cover state remain coherent after A completes.

2. **M0P1a-02 — High — scope change leaves other active scenes exposed during awaits.** `Madar/App/MadarLock.swift:140–149` (receiver: `ScenePrivacyPresenter.swift:35–44`). Only the initiating controller revokes synchronously. Other scene controllers/presenters hear about the change after both redaction and settings persistence return. An already authorized second scene can keep presenting protected content throughout a delayed scope change, contrary to the design's immediate invalidation of all affected presentations. **Fix:** synchronously broadcast a revocation at the start, before the first await, independently of publishing the successfully persisted scope. Each affected scene must cover and invalidate pending authorization immediately; commit the scope only after successful persistence, and handle failure without silently uncovering another scene. Add `test_M0P1a_scopeChangeImmediatelyRevokesOtherScene` using a delayed service; assert B is covered and its ticket invalid before resolving the delay, including the failure path.

3. **M0P1a-03 — Medium — cancellation does not invalidate a suspended request.** `Madar/App/MadarLock.swift:93–111`. Cancellation is checked only after `verify` or an active waiter resumes. A verifier is permitted to suspend without honoring task cancellation (the included continuation-based seam does exactly that); cancelling its task leaves `currentAuth` and `authenticating` alive and new requests busy. A request waiting for the scene to become active similarly has no cancellation wake-up. **Fix:** install a request-ID-guarded cancellation path that invalidates that authenticator, resumes/removes that request's lifecycle waiter, and clears only that request's state. A late result must remain stale and must not touch a newer request. Add controlled cancellation tests both during verification and while waiting through `.inactive`; require prompt invalidation and successful subsequent authorization without waiting for the old verifier to return.

4. **M0P1a-04 — Medium — late attachment loses an already-background lease boundary.** `Madar/App/ScenePrivacyPresenter.swift:46`. Every activation state other than `.foregroundActive` becomes `.inactive`. Attaching an already authorized controller to a `.background` scene therefore never records `backgroundAt` or performs background invalidation; on activation it can reuse authorization even after 60 seconds. **Fix:** map `.background` to `.background`, `.foregroundInactive` to `.inactive`, and handle `.unattached` fail closed; preserve an existing first background timestamp. Add a late-attach regression with an authorized controller and controlled clock that proves the 59/60-second boundary and invalidates a pending request when the observed state is background.
